GNSS 知识科普

GNSS 上的 PPS 引脚是干什么的？

一个每秒响一次、精度达纳秒级的"高精度节拍器"

01

一句话理解 PPS

PPS = Pulse Per Second，秒脉冲

GNSS 接收机在解算出卫星时间后，会每秒输出一个脉冲，脉冲边沿被校准到 GPS/北斗的整秒时刻，误差仅为几十到几百纳秒。它用来对外提供一个精确到纳秒级的时间基准。

三个典型用途

  • 1时间同步/校时：MCU 捕获 PPS 边沿对齐本地时钟。
  • 2授时打标：数据打上"第 N 秒"，多设备微秒级同步。
  • 3边沿触发：让某段逻辑动作发生在整秒上。
02

系统怎么连接：GNSS → MCU

两条链路各司其职：串口告诉你是哪一秒，PPS告诉你精确在哪一瞬，两者对齐即得高精度时间。

03

核心要点

PPS 只给边沿

它只保证"整秒边界精确"，不告诉你"是哪一秒"。具体秒值要靠 NMEA 报文里的 $GPGGA/$GPRMC 读取。

接外部中断

典型接法：PPS → MCU 的 EXTI 外部中断脚，上升沿进中断做校时，务必等首句有效定位后 PPS 才稳定。

可调可扩展

有的模块（如 u-blox）PPS 可配成固定频率的周期脉冲、甚至多路差分输出，用于更高要求的同步场景。

04

关键：怎么"破译" PPS 对应的是哪一秒

别忘了：PPS 只告诉你"现在是整秒"，它不开口说话，不会告诉你"是哪一秒"。那怎么知道每一声"当"到底对应几点几分几秒？把报幕员喊的秒数，贴到某一次响铃的瞬间上即可。

事件你记下的东西
PPS 响了一声（边沿触发中断）记录本地时间戳 ts₁
报幕员喊"现在是 12:34:56"（NMEA 报文）拿到秒值 56（UTC 时:分:秒）
下一次 PPS 又响一声记录 ts₂，此刻秒值应为 57

于是：12:34:56 这一秒，正好是 ts₁ → ts₂ 之间的这一秒。把"56"这个标签贴到第一次响铃的边沿上，之后每响一声你就知道"又精确定位了一秒"——纳秒级节拍就此建立。

一句话口诀

NMEA 告诉你是哪一秒，PPS 告诉你精确在哪一瞬。两个都对上，时间才又准又知道数。

两个工程坑

  • 1错一帧/半秒：有的模块 $GPRMC 报的时间和对上的 PPS 边沿差半秒或一帧，用前要实测校准偏移。
  • 2定位才算数：冷启动未拿到卫星时间时铃不响或不稳，等首句有效定位后再开始"贴标签"。

Q1 · PPS 先到、NMEA 晚到，怎么算？

关键在：用到的是 NMEA 文本里写的秒值，不是它到达的那一瞬。MCU 靠一个不停跳的本地计数器量"距 PPS 边沿过了多久"，把两者相加即可。 当前时刻 = 边沿所指秒(如 12:34:56.000) + 本地计数器距离 = 12:34:56.150 纳秒精度来自"距边沿时长"的精细计时，与报文何时到达无关。晚到 0.15s、甚至 2s，都不影响。

示意：PPS 边沿先到、报文晚到也能算

Q2 · 会不会存在 NMEA 先到、PPS 后到？

物理上不可能存在"报文本体先到、它对应的边沿后到"。因为报文是在整秒（边沿之后）才生成的，再加传输必然更晚。 如果你"先收到报文、才看到某个边沿"，那看到的那个边沿只能是下一个边沿 B(57.000)——它本来就不属于这条 56 报文。真正要关注的是"文本秒值指向哪一根边沿"，而不是先后顺序。

示意：对应边沿必然先到，报文晚到（真实只有这一种顺序）

Q3 · 报文晚到 0.8s，会不会错配到下一秒的边沿？

只有用"最近的边沿"这种省事判据才会错配到下一秒的边沿 B。正确判据是"文本写死的秒值 → 该秒所属区间的开头边沿"：报文文本 = 56 → 属于第 56 秒 → 开头边沿 = 56.000。B 是 57 秒的开头，归下一条"文本=57"的报文，不会串位。

示意：正确判据（文本秒值→开头边沿） vs 错误判据（最近边沿）

Q4 · 那个"前提"到底是不是"PPS 必须早于报文"？

不是。真正的关系是：对应边沿(这一秒的开头)必然早于报文本体，因为报文在它区间的开头边沿之后才生成——这是自动成立、无需假设的结论。若你发现模块存在固定半秒/一帧的相位差，那是厂商定义的固定偏移，只需联调时实测一次、写死常数，与"先后顺序"无关。

05

教案：卫星晚了 75ms，GNSS 怎么算出准确时间？

前几天你问过一个很关键的问题："卫星信号明明要飞 75ms 才到地面，GNSS 凭什么知道真正的整秒？"
答案不是"忽略了这 75ms"，而是"算出来了它"——GNSS 定位的本质，就是把传播延迟当一个未知数，和其它量一起解出来。按下面 4 步讲，顺序最清晰。

卫星发来的是准确时间没错，但信号在传下来的途中花了时间。GNSS 收到时，那个"准确时刻"已经过了——中间这段到底耗时多少？这就是下一节要解的核心谜题。

第一步

卫星信号自带「我几点发出的」

卫星播发的电文按卫星原子钟逐帧发出，接收机能测到"这帧是卫星时间几点几分几秒发的"。同时电文里带星历＋卫星钟差修正，告诉它：这颗星此刻在天上哪儿、它的钟和 GPS 时间差多少。

第二步

「解方程」把传播延迟算出来

接收机的晶振不贵也不准，它和真实 GPS 时间有个未知偏差 Δt。设 4 个未知数：(x,y,z) 位置＋Δt 钟差。每颗卫星给一个方程，所以要至少 4 颗卫星才能解出它们。

第三步

传播时间被「补偿」，不是被「忍受」

位置解出后，传播时间就是已知量：距离 ÷ 光速 ≈ 67~86ms，再修正电离层 / 对流层 / 相对论 / 卫星钟差。结论变成："那帧是 GPS 时间 T₁ 发出、走了 75.3ms，所以到达我这里的标准时间是 T₁ + 75.3ms。"

第四步

PPS 就是「对准后的钟」在打拍子

接收机用解出的时间偏差持续校准 / 驯服自己的廉价晶振，把它驯成原子钟的节拍。于是它精确知道下一个整秒何时到来，就在那一瞬间拉高 PPS 引脚——上升沿就这样对齐了整秒。

深入解析

那「真实时刻」到底是怎么算出来的？

数据包确实给了两样已知量：卫星发出时刻 T_sv、卫星位置 (x,y,z)_星。但还缺一个关键拼图——信号飞了多久。接收机另一只手量到的是本地钟读到的收到时刻 T_rx，而这个本地钟是廉价晶振、本身就不准（偏差 Δt）。于是：伪距 = (T_rx − T_sv)×光速 = 真实距离 ＋ c·Δt。真实距离由卫星位置（已知）和接收机位置（未知）决定，c·Δt 是钟偏造成的误差（也未知）。每颗星给一个方程，要解 4 个未知数 (x,y,z,Δt)，所以需要 ≥4 颗卫星。解出 Δt 后：真实时刻 = T_rx − Δt，GNSS 就用它对准下一秒 PPS。

先理解方向即可：数据包给已知位置+时刻 → 量出不准的 T_rx → 联立解出钟偏 Δt → 真实时刻浮出。

一句话：卫星"晚到"的 75ms 不是误差，而是解方程的原材料——位置和准确时间，本来就是同一组方程解出的两个副产品。

各个误差环节是多少量级？

环节误差量级
卫星原子钟纳秒级
传播延迟（~75ms）→ 被解方程算出并补偿残余误差 分米级
电离层 / 对流层修正残余纳秒 ~ 亚微秒
模块内部钟驯服亚微秒级
最终 PPS 边沿精度普通模块几十 ~ 100 纳秒级

USB 知识科普

USB 主机有什么用？

从设备插入到上手使用，主机是怎么一步步把设备"认出来"的

01

枚举（Enumeration）是啥意思

把"插上的电"变成"能用的设备"

枚举就是设备插进 USB 口后，主机把它认出来、问清楚、配好再交给系统使用的全过程。没枚举完，设备只是"带电但形同虚设"。

枚举按什么步骤走

  • 1检测插入：硬件捕捉电平跳变。
  • 2复位到地址 0：设备回到默认地址。
  • 3读描述符：自我介绍 VID/PID/接口/端点。
  • 4分配地址：发给设备唯一地址。
  • 5配置生效：加载驱动，进入可用状态。
02

主机怎么知道设备插进来了

不是轮询，是硬件电平检测 + 中断

主机 不是隔一段时间去"查"端口，而是靠信号线的物理特性由硬件电路自动捕捉。设备一插入，硬件立刻跳出中断，固件才被叫醒。原理如下：

问题答案
主机怎么知道设备插进来了？靠设备 1.5kΩ 上拉电阻把 D+ 或 D- 顶成高电平
是软件轮询吗？不是，是硬件电平检测 → 触发中断
空闲时为什么没动静？主机 15kΩ 下拉把 D+/D- 都压成 0
低速设备拉哪根？D-
全速/高速设备拉哪根？D+
主机 D+ / D- 都要下拉吗？都要接 15kΩ 下拉到地
03

这个"哪根被拉高"是谁规定的？

由 USB 规范（USB-IF）在硬件层固化

不是工程自创，而是 USB Implementers Forum（USB-IF） 在《USB 规范》电气章节里锁死的。主机双下拉、全/高速设备上拉 D+、低速设备上拉 D-，靠"哪根线变 1"来识别设备速度级别。

Wi-Fi 安全科普

WPA2：Wi-Fi 加密怎么保你上网安全？

每一项 Wi-Fi 密码的背后，都有一套让它"看不懂别人、也怕别人看懂"的加密协议

01

一句话理解 WPA2

WPA2 = 第二代 Wi-Fi 保护接入

WPA（Wi-Fi Protected Access，Wi-Fi 保护接入）是一个加密与认证协议族，用来保护无线数据不被窃听、不被篡改。WPA2 是其中被广泛使用的第二版，也是大家最熟悉的"Wi-Fi 密码"背后的加密标准。

它管了两件事

  • 1认证：确认"真的是你"， 通过密码校验上网者身份。
  • 2加密：让网上传的数据变成 别人看不懂的密文。
02

WPA 家族的演进

标准加密算法地位
WEP（远古）RC4（弱）早已被破解，勿用
WPA（第一代）TKIP过渡方案，安全性一般
WPA2（第二代）AES / CCMP当前主流，推荐
WPA3（第三代）AES / GCMP最新，正在普及

核心关键词：WPA2 用 AES 加密，取代了 WPA 的 TKIP 和 WEP 的 RC4，安全性跨代提升——这也是"选 WPA2/AES"比"选 WEP/TKIP"安全得多的原因。

03

WPA2 的两种工作模式

① WPA2-Personal（家用/小办）

也叫 WPA2-PSK。大家共用同一个预共享密钥（密码），用 PSK 握手（四次握手）协商出会话密钥。简单方便，是家用路由器的默认形态。

② WPA2-Enterprise（企业）

对接 802.1X / RADIUS 服务器，每个用户有独立账号。每个会话单独认证、密钥互相独立，一人一密，安全性更高，用于企业/校园网。

手上那台家用路由器，你设的"Wi-Fi 密码"通常就是 WPA2-Personal 的那个 PSK。

Git 协作科普

Git Rebase：提交历史为什么能"变"直？

同样是合并分支，merge 是"原地打结"，rebase 是"拆了重排"——一张图看懂两种历史观

01

一句话理解 Rebase（变基）

Rebase = 换个基底，重放提交

你的功能分支是从 main 某个旧点上"长"出来的。rebase 就是把你的提交一个个摘下来，接到 main 的最新顶端重新提交一遍——基底变了，所以叫"变基"。从此历史像一条直线。

它和 merge 的本质区别

  • 1merge：两个分支原地汇合，产生一个"合并提交"，历史保留分叉的真实形状。
  • 2rebase：重写历史，把分叉"拉直"，看起来就像你从最新代码上一次开发出来的。
02

一张图看懂：merge vs rebase

03

最常用的两个姿势

# 1) 同步主干后，把你的分支"搬"到 main 顶端
git switch feature-x
git rebase main          # 摘下你的提交，逐个重放到 main 最新处

# 2) 整理最近 3 个提交（合并 / 改名 / 删除）
git rebase -i HEAD~3
#   pick   a1b2c3  feat: 增加传感器驱动
#   squash 4d5e6f  fix: 修改变量名      ← 并入上一个提交
#   reword 7g8h9i  docs: 更新注释       ← 只改提交信息
#   drop   0j1k2l  chore: 临时调试      ← 直接丢弃

# 3) 重放途中遇到冲突：改完 → 暂存 → 继续
git add . && git rebase --continue
# 后悔药：git rebase --abort  一键回到 rebase 之前
交互式指令作用一句话类比
pick保留该提交（默认）原样通过
reword保留提交，但修改提交信息改简历措辞
squash并入上一个提交，信息合并保留两件事并成一件
fixup并入上一个提交，丢弃本条信息默默合并
drop直接删除该提交这段黑历史不存在
edit停在该提交，方便修改内容暂停检查
04

黄金法则：别动公共历史

只 rebase 自己的、没推出去的分支

rebase 会重写提交历史。如果对已经 push 到公共分支（如 main、共享分支）的提交做 rebase，别人 pull 下来会撞出大量重复冲突。历史一旦公开，就是团队契约——公共分支用 merge，私有分支随便 rebase。

冲突处理三步（会循环出现）

  • 1打开标了 conflict 的文件，手动改成想要的样子
  • 2git add 文件名 标记这个提交已解决
  • 3git rebase --continue 继续重放下一个

rebase 是一段一段重放的，所以冲突可能不止出现一次——耐心循环到它说 Successfully rebased。

实战案例：一次完整的变基实录

想要干嘛？（真实场景）

手上两个分支：develop/machine_S115 是同事维护的主开发分支，一直有新更新；feature/emerge_stop_secon_recover 是我的功能分支，但基于旧代码。我想继续在 feature 分支上开发，又不想丢掉 S115 的新更新——于是决定把 feature 分支变基到云端最新的 S115 上。

动手前的自查

  • 1基准选云端的 origin/develop/machine_S115，不用先切到它——fetch 后远程镜像就是最新
  • 2git status 确认工作区干净，没提交的改动先 commit 或 stash
  • 3心里有数：完成后推送要 --force-with-lease（历史被重写了）
# 0) 自查：工作区必须干净
$ git status
On branch feature/emerge_stop_secon_recover
Your branch is up to date with 'origin/feature/emerge_stop_secon_recover'.
nothing to commit, working tree clean

# 1) 一步同步云端所有分支（不用切分支、不动本地代码）
$ git fetch origin

# 2) 变基：把我的提交重放到云端 S115 最新处
$ git rebase origin/develop/machine_S115
Successfully rebased and updated refs/heads/feature/emerge_stop_secon_recover.

# 3) 历史被重写，普通 push 会被拒——用安全强推
$ git push --force-with-lease origin feature/emerge_stop_secon_recover
 + 2f36c33...adcf74c feature/emerge_stop_secon_recover -> feature/emerge_stop_secon_recover (forced update)
终端输出怎么读它
nothing to commit, working tree clean没有未提交改动，变基前提满足，可以动手
git fetch origin 无任何输出正常！fetch 静默完成，所有 origin/xxx 镜像已更新到云端最新
Successfully rebased and updated ...一次成功、零冲突——历史已重写成"一条直线"
+ 2f36c33...adcf74c ... (forced update)强推成功，+ 和 forced update 表明云端指针被移到新历史上
remote: Create pull request ...Bitbucket 主动给出 PR 链接——合并回 S115 时点它走正常审查

为什么用 --force-with-lease 而不是 --force？

--force 是无脑覆盖：云端有别人的新提交也会被抹掉。--force-with-lease 会先检查"云端还是我上次看到的那个版本吗"，不是就拒绝推送——本次变基后云端 feature 分支只有我自己在用，所以它能安全通过。

收尾必做：编译验证

变基后的代码是"最新基底 + 我的改动"的混合体，接口变更、宏被删这类问题只有编译能暴露。本次案例最后一步：立刻编译一遍固件确认通过，再点 remote 给出的 PR 链接发起合并请求。

BLE 低功耗蓝牙科普

NimBLE：ESP32 的蓝牙协议栈到底是个啥？

调一个函数手机就能连上来发数据——背后是一个"专业团队"在替你打工，它叫协议栈

01

协议栈是个啥？

一句话理解

ESP32 上的蓝牙射频，本质就是个会发电磁波的"喇叭＋耳朵"——只会收发 0 和 1，对方根本听不懂。协议栈就是"蓝牙规范的代码化身"：把怎么广播、怎么打包、怎么加密、怎么重传这一大堆规矩提前写成现成代码，打包给你用。规范是法律，协议栈是执法机构，你写的代码只是来办事的群众。

为什么叫"栈"（Stack）？

因为规矩不是一坨，而是分了层、一层摞一层，像叠盘子。每层只管自己那摊事：你说"开始广播"，下面每层自动接力把电波发出去。分层是为了互通——乐鑫的芯片、苹果的手机，只要每层都遵守同一套规范，说话就能听懂。

02

你干的事，在 BLE 里叫什么？

你说的BLE 术语角色
"发起蓝牙广播"GAP 广播（Advertising）ESP32 是外设（Peripheral）
"手机连接上 ESP32"建立连接手机是中心设备（Central）
"手机发数据到 ESP32"对特征值执行 Write走 GATT 数据模型
"ESP32 收到数据了"写回调被触发你的回调函数开始干活
"ESP32 主动给手机推数据"Notify / Indicate反向推送，无需手机轮询
03

ESP32 的两套协议栈，怎么选？

对比项NimBLEBluedroid
来源Apache Mynewt 项目移植从安卓系统移植
支持范围仅 BLEBLE ＋ 经典蓝牙（SPP/A2DP）
内存占用小（约省一半 RAM/Flash）大
API 风格简洁，事件集中一个回调接口较繁琐
适用只玩 BLE 首选（官方主推）需要经典蓝牙时才用

小彩蛋：Mynewt 怎么读？

读 "My-newt"（迈·纽特）。newt 是蝾螈，合起来谐音英文 minute（微小）——小巧得像只小蝾螈，正好呼应它"给小设备用的轻量系统"的定位。前面的 Apache 是 Apache 软件基金会（开源孵化组织）的名字。

04

数据怎么流：GATT "数据表格"模型

ESP32（外设 Peripheral）
 └── Service 服务（UUID 标识，比如"环境传感器服务"）
      └── Characteristic 特征值（真正的数据格子）
           ├── Read   读     → 手机读 ESP32 的数据
           ├── Write  写     → 手机发数据给 ESP32   ← 你用的就是这个
           └── Notify 通知  → ESP32 主动推数据给手机

手机"写数据"的那一瞬间，NimBLE 会调用你提前注册好的写回调函数，把 (连接句柄, 属性句柄, 数据指针, 长度) 递给你——你只管处理内容，传输细节一概不用操心。

06

新手必踩的三个坑

坑一：MTU 默认只有 23 字节

有效载荷只有 20 字节。手机要发大数据，得先协商更大的 MTU（监听 BLE_GAP_EVENT_MTU）。手机发数据"发不全"，八成是这个。

坑二：断开后要重新广播

手机断开连接后 ESP32 会"隐身"。要在 BLE_GAP_EVENT_DISCONNECT 回调里重新调 ble_gap_adv_start，否则断一次就得重启设备。

坑三：广播包只有 31 字节

设备名放不下是常态。解决办法：把部分内容放进扫描响应包（Scan Response），广播包＋响应包两段拼一起用。
